# Pick It Up — Architecture & Design Decisions

Technical/internal documentation for `Pick It Up` (React + TypeScript + Vite + Tailwind CSS v4). For what the app does and how to use it, see [README.md](README.md).

## Design Philosophy

A few principles recur across every UI decision in this codebase, worth stating explicitly since no single component makes them obvious on its own:

* **A small set of primitives, reused relentlessly.** New controls are built by extending an existing pattern rather than inventing a new one: `<ChoiceChip>` is `<Chip>` with exactly one thing removed (the checkmark); `MdCheckbox`'s hover halo is `DualRangeSlider`'s thumb "state layer" technique, applied to a second component; the Recognition drill's answer options are `<Button>` with a couple of new variants, not a bespoke class string; and the Glossary card's title button is a ModeSwitch lever side's exact visual treatment, applied to a single action instead of a two-way toggle.
* **Physical mechanisms, not flat components.** Controls are conceived as tactile objects with real geometry, not flat rectangles. `DualRangeSlider`'s halo overshoots its own track like a real slider thumb; the Production/Recognition mode toggle ("the lever") is a boxy, `rounded-xl` slab that deliberately overshoots the thin pill track it slides in on all four sides, so it reads as a distinct object riding *on* the track rather than a bigger pill nested in a smaller one.
* **Actionable titles, not decorated headings.** When a card's whole reason for existing is one action (or a small toggle's worth of actions), the title *is* the button — not a plain `<h2>` sitting next to a separate control. The lever's own sides are the original example (bold label + small caption, e.g. "Production" / "Tap to start", both inside one interactive slab); the Glossary card's title button ("Glossary" / "View Terms", styled and sized identically to a lever side) is the same pattern applied to a single action. A short subtitle *outside* the actionable element — never inside its caption — carries the contextual "what's going on right now" info (lesson/term counts, mastery progress) that would otherwise clutter the button itself.
* **Continuous input, discrete commitment.** Where a gesture has both a raw physical position and a discrete meaning attached to it, the two update on deliberately different schedules. The lever's drawn position (`dragFrac`) tracks the pointer unconditionally from the first pixel of movement, zero threshold, zero lag — a lever that hesitates before following the finger reads as broken. The *meaning* riding on that position (the caption's "abstain" state, the label color's commit-to-gray, the final mode on release) is threshold- or distance-gated and updates in discrete jumps instead, because flickering between two answers while the gesture is still visibly undecided feels worse than a slightly-delayed commit. See `ModeSwitch.tsx`.
* **Measure the rendered object, not its layout box.** Some elements are intentionally drawn larger or smaller than the CSS box a naive DOM read would suggest — the lever overshoots its own track via absolute positioning; `AnnotatedTerm`'s glyphs render at `0.7em` of their container. Spacing and sizing decisions have to be made against the *true visual extent*, not the box: matching another element's font size means matching what `AnnotatedTerm` actually renders at (≈0.7× its container), not the container's own class, and compensating for the lever's overshoot means accounting for its true 62px visual height, not its track's 44px flow-box.
* **Padding beats margin whenever the gap must not collapse or clip.** Two recurring bugs, one fix. First: an element's hover/focus halo bigger than its own row (`DualRangeSlider`'s thumb, `MdCheckbox`'s hit-area) overshoots an `overflow-hidden` ancestor that's there for an unrelated reason (clipping a slide-in animation horizontally), silently clipping the halo too. Second: adjacent sibling margins in normal block flow collapse to their *larger* value, not their sum — so compensating for a visual overshoot (the lever's) with a plain margin can silently lose most of its effect depending on what it's adjacent to. Both are solved the same way: padding (real, non-collapsible, non-clippable space) on a wrapper, paired with an equal negative margin when the wrapper's own footprint must stay unchanged for surrounding layout.
* **State, never refs, for anything read during render.** A value that both persists across renders (or across a gesture's lifetime) *and* needs to affect what's drawn belongs in `useState`, not a plain `useRef` read inline in JSX — React's hooks lint flags ref reads during render because a ref mutation alone doesn't guarantee a re-render happens at all. Refs stay reserved for pure imperative bookkeeping that's only ever read from inside an event handler, never from render (`draggedRef`, `cleanupRef` in `ModeSwitch.tsx`).
* **A utility class that doesn't exist fails silently, not loudly.** Tailwind generates no CSS — and raises no build error — for a class name it doesn't recognize. `animate-in`/`fade-in`/`slide-in-from-bottom-4` (utilities from the separate `tailwindcss-animate` plugin) were used throughout `Drills.tsx` without that plugin ever being installed; every one of those "animations" was actually an instant, un-animated pop-in, only caught by comparing it side-by-side against a transition that *did* visibly animate. Fixed by defining real keyframe-based utilities instead (`--animate-*` theme tokens + `@keyframes` in `index.css`) — see Critical Implementation Note D.
* **Borrowed authority, overridden on contact with reality.** Established design vocabularies (Material Design 2's chips, checkboxes, tab conventions) are a starting point, not a spec. A full MD2 reskin was tried app-wide, didn't hold up, and was rolled back to a near-monochrome slate-and-white system with one accent color — only the components that still worked in isolation were kept.
* **Structure and behavior are treated as design, not separate from it.** Passes like relocating the Verb Form toggle from the Glossary card to the Drill card (it affects what gets drilled, not what gets browsed), or folding the "session active" state into the same sliding-panel mechanism as everything else instead of a separate hard-cut card, happen in the same breath as visual polish — where a setting lives and what a control actually does are considered alongside how it looks.

## 1. File Architecture & Domain Model

The codebase is structured into cohesive, domain-specific "fat files" to limit import fragmentation and optimize clarity — plus a handful of small, deliberately single-purpose files for controls that are genuinely shared across more than one fat file (a checkbox and a `localStorage` hook don't belong to any one domain, so they don't live in one).

```
src/
├── assets/
│   ├── processed_vocabulary.csv     # Original raw CSV source (historical, unused at runtime).
│   ├── processed_vocabulary_2.csv   # Second raw CSV source, merged in (historical, unused at runtime).
│   ├── tableConvert.com_*.csv       # Source for verb dictionary-form data (historical, unused at runtime).
│   └── processed_vocabulary.json    # The only vocabulary file actually loaded by the app.
├── dictionary.ts                    # The Data Domain: Vocabulary type, database load, filtering/verb-form hooks, POS labels.
├── Canvas.tsx                       # The Hardware Domain: Isolated Apple Pencil and pointer-event writing canvas.
├── Button.tsx                       # The Button System: shared <Button> (filled) and <TextButton> (MD2 text button).
├── ModeSwitch.tsx                   # The Lever: draggable Production/Recognition hardware-style toggle + session launcher.
├── MdCheckbox.tsx                   # Shared boolean-toggle control (Material "state layer" checkbox), used by App.tsx and TermsList.tsx.
├── useLocalStorage.ts               # Generic localStorage-backed useState hook, shared by App.tsx and TermsList.tsx.
├── Drills.tsx                       # The Core Engine: Furigana/pitch rendering, Recognition/Production drills, DrillEngine, and FlashcardEngine.
├── TermsList.tsx                    # The Terms Viewer: Searchable, spreadsheet-style vocabulary browser with a marking control.
├── App.tsx                          # The Shell: Global settings, localStorage persistence, and the menu/drill/terms router.
├── main.tsx                         # React application entry point.
└── index.css                        # Global stylesheet: Tailwind CSS v4 import, theme tokens, keyframe animations, document-scroll lock.
```

## 2. Domain Specification

### 2.1 The Data Domain (`src/dictionary.ts`)

Houses the type system (`Vocabulary`, `AffixType`, `PosType`), loads the parsed database from `src/assets/processed_vocabulary.json`, and exposes the `useVocabulary(selectedLessons: Record<string, boolean>)` hook, which memoizes the filtered vocabulary list for a multi-select map of lesson IDs.

```ts
interface Vocabulary {
  id: string;
  raw_term: string;
  term: string;
  reading: string;
  definition: string;
  pitch_accent: number;
  affix_type: AffixType; // 'none' | 'prefix' | 'suffix'
  lesson_id: string;
  pos: PosType;          // English enum; see below.
  pos_raw: string;       // Original Chinese 詞性 label (e.g. 'ナ形容詞'), kept for traceability.
  dic_form?: string;               // Verbs only: dictionary (辞書形) form.
  dic_form_reading?: string;
  dic_form_pitch_accent?: number;
}
```

* **State Management:** This file is intentionally stateless and has no `localStorage` involvement. Statistics, the marked-terms list, and all other settings live in `App.tsx` (see 2.7), built on the shared `useLocalStorage` hook (now its own file, `src/useLocalStorage.ts` — see below).
* The raw CSVs under `src/assets/` are historical source snapshots only — the running app never reads them. New vocabulary is merged into `processed_vocabulary.json` by hand/one-off script when a new CSV batch arrives.
* **Part-of-Speech (`pos` / `pos_raw`):** Every entry in `processed_vocabulary.json` carries a `pos` field (one of `'verb' | 'na_adj' | 'i_adj' | 'noun' | 'adverb' | 'pronoun' | 'interjection' | 'conjunction' | 'pre_noun' | 'counter' | 'prefix' | 'suffix' | 'phrase' | 'other'`) and a `pos_raw` field (the original Chinese 詞性 label, e.g. `'ナ形容詞'`). These were backfilled from the `tableConvert.com_*.csv` source files using `enrich_pos.py`, a one-off preprocessing script at the project root. The script matches entries by (term, reading) exact pair, then by reading-is-dash fallback, then by term alone, with a final affix_type heuristic for unmatched entries.
* **`posLabel(v)` / `posRank(v)`:** `posLabel` maps a `Vocabulary` entry's `pos` to a short, chip-style English label (`Verb`, `な-adj`, `い-adj`, `Noun`, `Adverb`, `Pronoun`, `Interjection`, `Conjunction`, `Pre-noun`, `Counter`, `Prefix`, `Suffix`, `Phrase`, `Other`) — same visual language as the Word Type filter chips, used by the Terms Viewer's "Form" column. `posRank` returns that entry's index in a fixed `POS_ORDER` array (the five filter-chip categories first, in the same order the chips use, then the remaining pos values), used to drive the Terms Viewer's form-sort toggle with a single `Array.prototype.sort` — sorting is stable, so toggling it off always returns to the original (lesson/dataset) order rather than shuffling.
* **Word Type Filter:** The five user-visible filter buckets map as follows: `verb` → 動詞; `na_adj` → ナ形容詞; `i_adj` → イ形容詞; `noun` → 名詞; `other` → everything else (adverbs, pronouns, phrases, affixes, etc.). `wordTypeOf(v)` maps a `Vocabulary` entry to its bucket. `filterByWordType(vocabList, selectedWordTypes)` narrows a list to the active bucket selection. `App.tsx` applies this to `activeVocab` before `applyVerbForm`, so it composes with the lesson scope and affects both drill modes and the Terms Viewer identically.
* **Verb Form Toggle:** `applyVerbForm(vocabList, useDicForm)` swaps a verb's `term`/`reading`/`pitch_accent` over to its `dic_form`/`dic_form_reading`/`dic_form_pitch_accent` when the toggle is on, leaving every other field (and non-verb entries, which lack `dic_form`) untouched. `App.tsx` applies this once to `activeVocab`/`sessionVocab`/`displayVocab` before handing them to a drill engine, so neither engine needs to know which form is active. The Terms Viewer is a deliberate exception — see 2.6.
* `isVerb(v)` remains exported for backward compatibility and now reads `v.pos === 'verb'` instead of the previous `v.dic_form !== undefined` heuristic — both are equivalent on this dataset but `pos` is now the canonical source of truth.

### 2.2 The Hardware Domain (`src/Canvas.tsx`)

Encapsulates low-level canvas context interactions and pressure-sensitive drawing (`<DrawingCanvas>`). It is decoupled from game state, returning a pure canvas element plus a global `clear` handle.

* **Fixed Aspect Frame:** The canvas box is a centered `w-[80%]` panel constrained to `aspect-[4/3.75]` and `max-h-[41vh]`, so it keeps a consistent writing area across drill types instead of stretching to fill the viewport.
* **Palm-Rejection Integrity:** All interactive canvas elements (clear button, evaluation buttons) strictly enforce Apple Pencil gating (`pointerType === 'pen'`) combined with `select-none touch-none` CSS utility locks. An `allowMouse` debug flag can widen this to also accept `pointerType === 'mouse'` for development on a trackpad.
* **Disable Lock:** An optional `disabled` prop applies `pointer-events-none` to the canvas's shared parent `<div>`, disabling both drawing and the clear button in one shot. Used by `<ProductionDrill>` to force grading before the canvas can be touched again.
* **Cursor:** The clear button carries an explicit `cursor-pointer` — like every other clickable in the app, since a plain `<button>`'s user-agent default cursor is `default`, not `pointer` (see Critical Implementation Note E).

### 2.3 The Button System (`src/Button.tsx`)

The shared shape for every non-specialized clickable action in the app. Two components, both intentionally excluding `Chip`/`ChoiceChip` (selection pills, whose coloring *is* a selection state, not an action — they stay bespoke in `App.tsx`) and the Recognition drill's pitch-accent number pad (kept as its own small circular control — see 2.5).

* **`<Button>`** — the filled button. `h-11` fixed height by default, `rounded-xl`, `shadow-md`, and a press animation (`active:scale-95`, on the bare `transition` utility so both `transform` and `background-color` animate) applied uniformly regardless of variant. Variants: `primary` (the app's one "primary action" color, `bg-slate-800`), `outline` (neutral resting look, used for an unselected/unevaluated state), `correct`/`incorrect` (strong green/red feedback — deliberately separate from `success-outline`/`danger-outline`, which use a lighter, more inviting resting look for the Production drill's *grading* buttons; sharing one variant between "pick the right answer" feedback and "grade yourself" invitation would have made one of the two read wrong). An `autoHeight` prop swaps the fixed `h-11` for `py-3 min-h-11`, for the rare case where content genuinely needs to wrap (the Recognition drill's answer options, whose definitions can run to a full sentence) rather than clip.
* **`<TextButton>`** — the MD2 "text button": no fill or border at rest, just the label's own color; a translucent "state layer" background (same halo technique as `MdCheckbox`/`DualRangeSlider`) fades in on hover and deepens on press. Same `h-11`/`rounded-xl`/`px-4` footprint as `<Button>` so tap targets stay consistent everywhere, filled or not. An `align` prop (`'start' | 'end' | 'center'`, default `'center'`) offsets the label by `-ml-2`/`-mr-2` — deliberately **half** of the `px-4` clickbox padding, not the full amount: a full cancellation would make the label sit exactly as if the clickbox didn't exist ("text-aligned"); no offset leaves it exactly clickbox-inset; half was the chosen middle ground after trying the full offset and finding it read as *too* flush against the edge it's anchored to. Used wherever a `TextButton` needs to visually anchor to a container edge it isn't centered in — "Back to Menu" (start), "Exit Drill" ×2 (start), "Discard Drill" (end).
* **Recognition drill answer options** (`Drills.tsx`) select a `Button` variant per option per render, rather than toggling a class string: `outline` (resting/unselected) → `primary` (selected, awaiting evaluation) → `correct`/`incorrect` (post-evaluation, this option specifically) or `outline` again with a plain `opacity-50` + `pointer-events-none` (post-evaluation, neither correct nor selected). The faded look is applied as an unconditional class, **not** via `<Button>`'s own `disabled` prop — `disabled:opacity-50` is a pseudo-class rule, and pseudo-class specificity would have washed out the `correct`/`incorrect` variants' own colors too if `disabled` had been used uniformly across all six options. `pointer-events-none` (not the `disabled` attribute) is what actually blocks further clicks post-evaluation; the click handler already no-ops once evaluated regardless.

### 2.4 The Lever (`src/ModeSwitch.tsx`)

The Production/Recognition mode switch — a hardware-style toggle that also doubles as the session launcher (tapping the already-active side launches/resumes that mode; tapping the other side just switches). See the Design Philosophy bullets on **actionable titles**, **continuous input vs. discrete commitment**, and **state over refs** above — this file is where all three were established. A few implementation specifics worth calling out beyond those:

* **Geometry:** The track is a thin, fully-rounded pill (`h-11`); the lever is a separate `absolute`-positioned `rounded-xl` slab layered on top, overshooting the track by `9px` on every side (`top`/`bottom: -9px`, and a matching small horizontal overshoot baked into its `left`/`width` formula) so it reads as a distinct object riding *on* the groove rather than a bigger pill nested in a smaller one.
* **Drag vs. tap disambiguation:** `pointerdown`/`move`/`up` listeners live on the *track*, not the (pointer-events-none) lever, so dragging works from anywhere in the switch. Deliberately **not** `setPointerCapture` + React's `onPointerMove`/`Up` props — capturing the pointer on the track retargets the browser's synthetic "click" event to the track itself instead of whichever button is under the finger, silently breaking plain taps. Plain `window.addEventListener` pairs, added/removed per-gesture, track the pointer just as reliably without touching how clicks get targeted. A drag that wanders away from and back to its starting button would otherwise fire a spurious click (native behavior: a click only fires if pointerup lands on the same element pointerdown started on) — `justDraggedRef` swallows exactly that one trailing click whenever a real drag occurred, self-healing on the next `pointerdown` in case a prior gesture's release was ever missed.
* **The abstain state:** Past a small drag threshold (`DRAG_THRESHOLD_PX`) and short of a resolved release, the switch "abstains" (`isAbstaining`/`isDragging`) — neither side reads as `isActive`, so the caption doesn't pop to an answer the gesture hasn't committed to. The label color goes further: it eases continuously for the first `ABSTAIN_SNAP_FRACTION` (10%) of the drag away from its starting side, then **snaps to and holds** fully neutral gray (`pastAbstainThreshold`) for the rest of the gesture, regardless of further movement — a deliberate two-speed design (a fast continuum, then a hard commit) rather than either a live full-track continuum (visually "chases" the pointer the whole way, reads as indecisive) or an instant binary flip (loses the "I'm mid-gesture" feedback entirely).
* **Two-speed caption transition:** The caption's `grid-template-rows` collapse animation runs at `100ms` when collapsing *into* abstain (fast enough to finish before a normal-speed drag reaches the other side) but `200ms` when expanding back *out* of abstain on release (no lever to race there, so it can take its time). An earlier attempt disabled the transition entirely during drag to fix a "label doesn't finish recentering" bug — the real fix was making it fast, not making it instant.

### 2.5 The Core Engine (`src/Drills.tsx`)

Bundles rendering helpers and both drill/session engines:

* `<AffixWrapper>`: Contextually formats prefixes (`お～`) and suffixes (`～さん`) — see the Affix Rendering Rules below.
* `<AnnotatedReading>`: Renders a reading string with the pitch-accent overline applied over the correct span of morae.
* `<AnnotatedTerm>`: Renders the term with per-segment furigana (`<ruby>`/`<rt>`) over kanji spans, aligning each kanji run against its slice of the reading via regex segment-matching, and falling back to one whole-term ruby block if segment alignment fails. The term's own glyphs render at `0.7em` (via a sibling `<span>`) to stay visually smaller than the furigana sitting above them — `<rt>`'s own `em` unit is relative to the `<ruby>`'s (unscaled) inherited font-size, so this never shrinks the furigana itself. Takes an optional `compact` prop (`marginBottom: 0.05em` instead of the default `0.2em` on the `<rt>`) — the default gap was tuned for the Drills' large-scale prompt display, where extra breathing room reads fine; the Terms Viewer's dense table rows use `compact` to keep the furigana visually attached to its kanji instead of floating.
* `<RecognitionDrill>`: Renders a 6-option multiple-choice question (1 correct + 5 randomized distractors) in one of 2 modes, chosen randomly per question by `<DrillEngine>`:
   * `Reading → Meaning`
   * `Meaning → Reading`

  After evaluation, the complement (reading or meaning) is revealed as an absolutely-positioned annotation beside the prompt (`animate-fade-in`, see Critical Implementation Note D), so the prompt itself stays perfectly centered. The 0–6 pitch-accent selector pad stays visible throughout (always testable, never blocking submission) and color-grades green/red against the correct value once evaluated; a `pitch_accent === -1` term instead shows a locked "Pitch Accent N/A" placeholder. The six answer options are `<Button>`s (see 2.3); the pitch-accent pad stays a bespoke `w-10 h-10 rounded-full` circle — a chip/pill treatment was considered and deliberately rejected (kept as-is, just given the same `active:scale-95` press animation as every other button, so the *feel* is consistent even where the *shape* isn't).

* `<ProductionDrill>`: Integrates the drawing canvas and a Correct/Incorrect self-grading step. Always drills `Meaning → Term` (writing the term freehand). Tapping "Reveal Answer" shows the term (with furigana) vertically centered beside the prompt, offset by `ml-12` (`animate-fade-in`), and locks the canvas (`pointer-events-none`) so the user must grade before touching it again.
  * **Correct:** advances immediately (`onComplete(true)`).
  * **Incorrect:** does *not* advance. It unlocks the canvas for correction and swaps the button row for a single "Proceed" button (guarded by the same 400ms mis-tap delay as the reveal step; entrance via `animate-fade-slide-up`). Only pressing "Proceed" calls `onComplete(false)`, which triggers the streak-reset/requeue logic in `<FlashcardEngine>`.

* `<DrillEngine>`: Powers Reading Recognition sessions.
  * **Session Length:** Always builds a fixed 15-question queue per session. When the pool has ≥ 8 terms (i.e. `pool × 2 ≥ 15`), no term appears more than twice — the queue is assembled pass-by-pass, each pass contributing at most one slot per term via the weighted draw, stopping at 15. When the pool is smaller than 8, the per-term cap is lifted and terms repeat as needed to reach 15 (or fewer if the pool is tiny and exhausts all repetitions). There is no recursive "mistakes queue" — errors are deferred entirely to the global `stats` dictionary for future weighted selection.
  * **Weighted Selection:** Each pass computes the **Laplace-smoothed correctness rate** `(correct + 1) / (attempts + 2)` for every in-scope term. Terms in the lowest 50% tier of these rates get a **3x probability weight** over the remaining 50% via the `random() ** (1/weight)` Gumbel trick. The weight is recomputed independently per pass, so pass 2 is not a deterministic copy of pass 1.
  * **Progress UI:** A dot progress bar pinned to the right of the top bar, with a `<TextButton align="start">` "Exit Drill" on the left.

* `<FlashcardEngine>`: Powers Production sessions. No fixed session length and no weighted selection — instead it maintains a rotating **working set** bounded by `[minWorking, maxWorking]`:
  * On each refill (triggered when a term is mastered and removed from the working set), it tops the set back up to `maxWorking` with shuffled, not-yet-mastered terms. If the pool of fresh terms cannot bring the set to `minWorking`, it backfills with already-mastered terms (marked "permanent" so they don't get re-mastered, just recycled to keep the rotation full). The `useEffect` initialiser only fires when `workingIds` is empty (i.e. session start), so changing `minWorking`/`maxWorking` mid-session has no effect — but those controls are hidden while a session is active anyway (see 2.7).
  * A term is **mastered** (`isMastered`) once it's answered correctly on the very first attempt, or once it reaches a correctness **streak of 2** — an incorrect answer resets that term's streak to 0 and requeues it at the back of the rotation.
  * The session ends once every in-scope term is mastered. Flashcard attempts write to their own `fcRecords` (`{ attempts, streak }` per term) and never touch the global Recognition `stats` dictionary.
  * **Progress UI:** `{masteredIds.size} / {vocabList.length} mastered` counter pinned to the right of the top bar, with a `<TextButton align="start">` "Exit Drill" on the left. "Exit Drill" only navigates back to the menu (`appState: 'menu'`) — it does *not* end the session (`fcActive` stays `true`), so it doubles as a quick way to check the Terms Viewer or browse lessons mid-session without losing progress. Discarding is a separate, explicit action (see 2.7's Drill Card).

### 2.6 The Terms Viewer (`src/TermsList.tsx`)

A spreadsheet-style grid over the active lesson/word-type scope (`Term | Meaning | 辞書形 | Form`), live-searchable by term/reading/meaning (including dictionary-form spellings). Reuses the Core Engine's furigana renderer, `MdCheckbox`, and `useLocalStorage` rather than any bespoke rendering of its own.

* **Production form (furigana) on `Term`:** The Term column renders through `<AnnotatedTerm compact>` (see 2.5) instead of a plain string — furigana + pitch-accent overline, the same "production form" the drill itself reveals, rather than a separate plain-text Reading column repeating the same information. `compact` keeps the furigana visually attached to its kanji instead of floating with the wider gap tuned for the Drills' large-scale display.
* **Two independent form columns, not a stacked one:** `Term` always shows the ます形 form; a separate `辞書形` column (same text size/color/weight as `Term` — deliberately *not* muted, since a stacked single-column "primary form, smaller secondary form underneath" was tried first and produced four visually cramped lines per verb) shows the dictionary form when the entry has one, empty otherwise. Column order is `Term → Meaning → 辞書形 → Form`. `vocabList` is always the raw, pre-verb-form-swap array (`scopedVocab`, not `displayVocab` — App.tsx passes the *pre*-swap list specifically so both forms are always available here, regardless of what the Home screen's own toggle is currently set to), and the Meaning column is sized (`text-base`) to match `AnnotatedTerm`'s actual ~0.7×-scaled rendered glyph size, not the Term container's own `text-2xl` class (see Design Philosophy: measure the rendered object).
* **Phone-width toggle, hidden on iPad and mid-session:** The `辞書形` column is `hidden md:block` — there isn't room for two term columns on a phone-width screen, so phones instead get a single Term column plus a small `MdCheckbox` above the table (`md:hidden`) that switches which form that one column shows. The checkbox — and the whole concept of switching displayed form — is hidden whenever a Production session is active/paused (`!sessionActive`), independent of which mode is currently selected on the lever: this is a pure *display* preference, entirely decoupled from `nd_useDicForm` (the Home screen's own toggle, which actually determines drill content) and persisted separately (`nd_termsShowDicForm`, seeded from the Home screen's current setting via a `defaultUseDicForm` prop but never writing back to it).
* **Marking:** Clicking anywhere on a row toggles a "marked" highlight (`bg-md-accent-light`, i.e. Material Pink 50) — a lightweight, private way to flag terms for attention with no effect on drill selection. This is the app's one deliberate use of the accent color, kept distinct from the near-monochrome slate system used everywhere else.
* **Practicing View (Production, session-active only):** A second tab, "Practicing", filters the grid down to terms that aren't yet mastered (derived live from `fcRecords`/`isMastered`, the same session-mastery data the Flashcard engine itself tracks — there's no separate manual mastery toggle). `showTabs = mode === 'production' && sessionActive` — the tabs only appear while a Flashcard session is actually in progress, since "Practicing" has no meaning without a session to be practicing toward.
* **Back button:** `<TextButton align="start">`, not a plain `<button>` — same button system as everywhere else in the app, offset to visually hug the card's left edge (see 2.3).
* **Form sort:** Clicking the "Form" header toggles a stable sort by `posRank` (see 2.1) — stable, so toggling back off exactly restores the original (lesson/dataset) order rather than reshuffling.

### 2.7 The Shell (`src/App.tsx`)

Coordinates top-level state and routes between the menu screen, the Terms Viewer, and an active drill session (`appState: 'menu' | 'drill' | 'terms'`). `useLocalStorage` (now `src/useLocalStorage.ts`, shared with `TermsList.tsx`) is what every piece of persisted state below is built on top of.

* **Design System:** An earlier pass reskinned the whole app in a Material Design 2 "Indigo + Pink A200" palette (an app-wide `colorPrimary` on every button/tab/slider, `uppercase` button labels, MD button-height conventions), but it didn't land well as a whole and was rolled back — buttons, tabs, and the slider are back to the original near-black (`bg-slate-800`/`text-slate-800`) styling, normal case. Two pieces of that experiment stuck around because they read well on their own, decoupled from the app-wide primary-color idea, and were later extracted into their own shared files as the app's button/control vocabulary consolidated (`<Button>`/`<TextButton>` in `Button.tsx`, `<MdCheckbox>` in `MdCheckbox.tsx` — see 2.3):
  * `<Chip selected onClick>` (still local to `App.tsx`, deliberately not folded into the Button System — its coloring *is* a selection state, not an action): a fully-rounded (`rounded-full`), `h-8` (32px) filter chip — `bg-white`/`text-slate-600` unselected, `bg-slate-200`/`text-slate-800` selected, plus a leading checkmark. Purely grayscale, no accent color. Used for every multi-select filter (Lessons, Word Type). `<ChoiceChip>` is the same shape with the checkmark removed, for the single-select Verb Form pair.
  * `<MdCheckbox checked onChange>`: an 18px square, 2px-border checkbox — black fill + a white `lucide-react` `Check` icon when checked, a plain white box with a gray border (darkens on hover) when not. The `<button>` itself *is* the full 40px halo/hit-area (not just the 18px visual box) — the 18px box is a plain inner `pointer-events-none` `<div>`, since a `<button>` can't nest another `<button>` — so a click anywhere in the halo registers, not just on the small visual square. Used for both the Strict Pitch Accent toggle here and the Terms Viewer's phone-only form toggle (see 2.6).
  * `src/index.css`'s `@theme` block registers `--color-md-accent-light: #FCE4EC` (Material Pink 50, the Terms Viewer's marked-row highlight) and `--color-md-accent: #E91E63` (Material Pink 500, the pink `<TextButton>` variant's label/state-layer color) — the app's one deliberate accent color, used only for "Discard Drill" and the marked-row highlight.
* **Mode Toggle:** A single Production / Reading Recognition switch (`activeMode`, driven by the lever — see 2.4) determines which engine `appState === 'drill'` renders. Both modes share one scope — one lesson selection (`selectedLessons`) and one word-type selection (`selectedWordTypes`) — there is no independent per-mode scope, and no term can be permanently hidden from within the app (editing `processed_vocabulary.json` directly is the intended way to drop a term for good).
* **Glossary Card:** An actionable-title button (`w-full`, styled and sized identically to a lever side — see Design Philosophy) replaces what used to be a plain `<h2>Glossary</h2>` next to a separate "View Terms" button — tapping it opens the Terms Viewer, disabled when the current scope has zero terms. Its subtitle (`{n} Lessons Selected • {m} terms loaded`), left-aligned underneath, mirrors the Drill Card's own subtitle placement and gap (`mt-3`) below its lever, so the two cards' actionable-title-plus-subtitle pairs visually line up. Below that: "Lessons" and "Word Type" filter sections (`<Chip>`s, `text-xs font-semibold text-slate-400 uppercase tracking-wider` section labels). The card stays fully live and editable at all times, including while a Flashcard session is in progress — see Session Scope Snapshot below for how that's made safe. Sized `md:col-span-6`, matching the Drill Card, so the two cards (and their actionable-title elements) are the same width.
* **Drill Card:** Also `md:col-span-6`. The lever sits inside a `py-[9px]` wrapper (see Design Philosophy: padding beats margin, and Critical Implementation Note F) so the surrounding gaps (to the card's top edge, and down to the subtitle below) measure against the lever's true 62px visual height rather than the track's smaller 44px flow-box. Below the lever, one subtitle line does double duty: `'Load terms from the glossary'` when idle, or `{sessionMasteredCount} / {sessionVocab.length} mastered` whenever a Production session is active — same slot, same styling, whichever is relevant. Below that, a single **sliding panel** (two `<div>`s stacked in the same CSS grid cell, `translate-x` + `opacity`, `duration-200 ease-out`, `p-3 -m-3` for halo clearance — see Critical Implementation Note E) shows mode-dependent content:
  * *Production slot:* **Working Terms Range** (the `DualRangeSlider` below) when idle, or a single right-aligned **Discard Drill** `<TextButton variant="pink" align="end">` when a session is active. This is a deliberate consolidation — the app used to have an entirely separate "Session Status" card (a different top-level ternary branch swapping out the whole Drill Card) for the active-session case, which meant switching Production↔Recognition while a session was active hard-cut between two disconnected DOM trees instead of sliding, unlike every other lever-driven transition in the app. Folding "session active" into just another state of the *same* production-slot content restored the slide for that transition too.
  * *Recognition slot:* **Strict Pitch Accent** (`<MdCheckbox>`).
  * Below the sliding panel, **Verb Form** (`<ChoiceChip>` pair, ます形/辞書形) sits as a static, non-sliding section — it applies to both modes equally (both drill engines read the same `useDicForm`), so it isn't part of the slide transition, just a plain section underneath. Hidden whenever a session is active/paused (`!fcActive`), regardless of which mode is currently selected: a paused Production session's vocab reads this setting live, so leaving it editable mid-session would silently change that session's content out from under it. (This toggle lives here, not in the Glossary card, precisely *because* it affects drill content, not browsing — see Design Philosophy: structure and behavior are design.)
* **Dual Range Slider (`DualRangeSlider`):** Two overlapping native `<input type="range">` elements drive value/drag logic only — their thumbs are made fully invisible (`bg-transparent`, no drawn pseudo-element) and widened 44px beyond the track (`left`/`right: -22px`) so each one is a Material-Design-style invisible touch target. The visible dot, its filled track, and its focus/hover halo (`bg-slate-800`) are separate plain `<div>`s positioned at a plain `frac * 100%` + `translate(-50%, -50%)`, sharing the exact same widened reference frame as the (invisible) native inputs — this sidesteps relying on any given browser's internal "keep the thumb inside the track" inset math, so the dot's center always lands exactly on the track's true ends, never past them, in every browser. The halo is a `peer/min`/`peer/max`-driven `opacity` transition (`peer-hover:opacity-100 peer-focus:opacity-100 peer-active:opacity-100`) rather than a pseudo-element background, since `opacity` animates reliably cross-browser where a radial-gradient background swap does not. The `peer-active` class is required for iPadOS Safari, which does not fire `:hover` (no cursor) and may not reliably fire `:focus` on range inputs from touch; `:active` fires on every touch interaction, so the halo appears correctly on iPad. A z-index heuristic (whichever thumb's value is on the far side of the range's midpoint gets a higher z-index) keeps the correct thumb grabbable when the two are close together. Rather than a separate collision/gap mechanism, `App.tsx` simply clamps each `onChange` handler so `valueMin` and `valueMax` can never become equal (`Math.min(next, valueMax - 1)` / `Math.max(next, valueMin + 1)`) — two overlapping handles can't happen in the first place. iPadOS Safari specifically draws a UA default `box-shadow` on `::-webkit-slider-thumb` (its native focus/active glow) that survives `appearance-none` plus a transparent background, showing up as a stray shadow under the decorative halo; both the pseudo-element and the `<input>` itself carry an explicit `shadow-none` to clear it (a reasoned fix for a real device quirk that can't be verified from this Chromium-only dev environment).
* **Session Scope Snapshot:** `selectedLessons`/`selectedWordTypes` always drive the home screen's live counts and the Terms Viewer, in and out of a session. A Flashcard session instead reads from a separate, once-per-session snapshot — `fcSessionLessons`/`fcSessionWordTypes` — captured only at the moment a session starts (`fcActive` transitions `false` → `true`, not on resume, which reuses the existing snapshot). `FlashcardEngine` is always fed the snapshot-derived `sessionVocab`, never the live `displayVocab`. This lets the Glossary card stay unlocked mid-session: editing filters changes what the Terms Viewer shows, but can never leave a running session's working set referencing terms that fell out of scope, since the session doesn't read the live filters at all.
* **Persistence:** Active mode, selected lessons, selected word types, both settings panels' values, marked terms, the Flashcard working-set bounds and per-term `fcRecords`, the global Recognition `stats` dictionary, and the Terms Viewer's own display-form preference are all persisted across sessions/reloads via `localStorage`.

## ⚠️ CRITICAL IMPLEMENTATION NOTES ⚠️

### A. Affix Rendering Rules

The application must strictly shield the user from ever having to manually draw the `～` symbol. The `affix_type` (`prefix`, `suffix`, or `none`) must dictate UI rendering under the following strict rules:

1. **In Recognition Drills (Multiple Choice):**
   * The affix is rendered inline as part of the text string prompt.
   * *Suffix example:* `さん` is rendered as `～さん`.

2. **In Production Drills (Canvas Writing):**
   * The affix is rendered as a static UI typography element **inside** the drawing canvas, providing contextual framing.
   * *Prefix example:* `[ CANVAS ～]`
   * *Suffix example:* `[～ CANVAS ]`
   * The user is *only* expected to draw the core `term` or `reading` inside the canvas itself.

### B. Pitch Accent Rules & Notation

Pitch accent UI (0–6 number pad) is integrated **only into Recognition Drill mode**. In Production Drills, the number pad is omitted entirely — the user is expected to draw the pitch accent overline directly onto the canvas alongside their handwritten reading.

* **The Test UI is Always Displayed:** In Recognition mode, the pitch-accent selector is visible but never blocks submission; the user can submit without selecting a pitch.
* **Unavailable Targets (-1):** When a term's `pitch_accent` is strictly `-1`, no pitch accent applies. The entire pitch UI is visually locked (`opacity-50`, `pointer-events-none`) and shows a `"Pitch Accent N/A"` placeholder instead.
* **Post-Answer Annotation (Overline Notation):** Immediately after answering/revealing, the reading is annotated with an overline spanning exactly the number of morae dictated by `pitch_accent`. All reading targets receive this annotation.
  * **0–6 Grading:** After a Recognition answer is evaluated, the pitch buttons stay on screen but color-grade: the correct pitch glows green (`bg-green-50 border-green-500 text-green-700`); an incorrect selection glows red (`bg-red-50 border-red-500 text-red-700`).
* **Reveal Mechanics (Production):** Tapping "Reveal Answer" shows the correct term — with furigana and pitch overline — vertically centered beside the prompt (not overlaying the canvas), so handwritten strokes stay visible for comparison. The canvas is locked until the user self-grades.
* **Furigana Scaling:** Term glyphs render at `0.7em` relative to their furigana (see `AnnotatedTerm` in 2.5) so the reading annotation reads clearly above smaller kanji, without shrinking the `<rt>` furigana itself. The gap between the two (`<rt>`'s `marginBottom`) is `0.2em` in the Drills' large-scale display, `0.05em` (`compact`) in the Terms Viewer's dense table rows.
* **Typography:** English/non-Japanese prompts and meanings use the injected `Noto Serif TC` typeface, decoupling them visually from Japanese characters and bypassing unreliable system font substitutions. The top-level app header uses `Space Grotesk` at 700 weight for branding.

### C. Layout Constraints

* **Viewport Boundaries:** The app's root layout must strictly use `h-[100dvh]` combined with controlled overflow (`overflow-y-auto` or `overflow-hidden`), ensuring the app perfectly locks to the available vertical space of mobile and tablet screens without expanding the body height unnecessarily.
* **Outer document scroll lock:** `html`/`body` are set to `height: 100%; overflow: hidden; overscroll-behavior: none` in `index.css` (with `#root` at `height: 100%`), so the outer document itself can never scroll or rubber-band on any device — only the app's own `overflow-y-auto` `<main>` panels (the menu screen, the Terms Viewer) can scroll, and only when their own content genuinely overflows. Both of those `<main>`s additionally carry `overscroll-y-contain`, so an iOS rubber-band gesture at the top/bottom of a long scrollable list can't visually "leak" a bounce up to the (locked) ancestor either. The Drill screens' `<main>`s use `overflow-hidden` and need neither — they never scroll, so there's nothing to chain.

### D. Animation & Motion System

* **Real utilities only.** `index.css`'s `@theme` block defines two keyframe-based animation utilities as Tailwind v4 `--animate-*` tokens: `animate-fade-in` (`fade-in 200ms ease-out`) and `animate-fade-slide-up` (`fade-slide-up 200ms ease-out`, entering from `translateY(1rem)`). These replaced a set of `animate-in fade-in slide-in-from-bottom-4 duration-300` classes throughout `Drills.tsx` that looked plausible but were silently inert — see Design Philosophy: a utility class that doesn't exist fails silently. **Before adding or trusting any Tailwind utility that looks like it might come from a plugin** (`animate-in`, `slide-in-from-*`, anything not in Tailwind's own core), verify the plugin is actually listed in `package.json` — it currently is not, and every animation in this app is either a hand-written `transition-*` class or one of the two `--animate-*` tokens above.
* **One consistent speed.** Both tokens intentionally match the `200ms ease-out` already used for the Drill Card's production/recognition sliding panel (see 2.7), so a reveal moment inside a drill and the settings-panel slide outside one read as the same animation system rather than two different speeds.

### E. Halo/Overshoot Clipping Technique

Recurring pattern, three call sites so far (`DualRangeSlider`'s thumb halo, `MdCheckbox`'s hit-area halo, both inside the Drill Card's sliding panel — see 2.7): a control's hover/focus halo is deliberately larger than the row it lives in (a Material "state layer" convention), but an ancestor needs `overflow-hidden` for an unrelated reason (clipping the sliding panel's horizontal translate). The fix is always the same shape: `p-3 -m-3` (or the axis-specific equivalent) on the `overflow-hidden` element itself — padding pushes the actual clip boundary outward past the halo on every side; the exactly-equal negative margin pulls the element's own footprint back to what it was, so nothing about surrounding layout shifts. Reach for this whenever a decorative halo/glow gets visibly cut off by a container that has `overflow-hidden` for a different reason than clipping that halo.

### F. Margin Collapsing Gotcha

Adjacent sibling margins in normal block flow **collapse to their larger value, not their sum** — this bit the fix for the lever's overshoot (2.4/2.7) once already. A first attempt compensated the lever's 9px visual overshoot with `margin-top`/`margin-bottom` directly on the track: the top side worked (the card's own `padding` blocks parent↔child margin collapsing), but the bottom side silently collapsed with the subtitle's `mt-3` down to `max(9px, 12px) = 12px` instead of the intended `9px + 12px`, under-correcting by 9px. The fix was `padding` (never collapses) on a wrapper `<div>` around the lever instead of `margin` on the track itself. Whenever a spacing fix "half works" — one side visibly correct, the other side not — check for margin collapsing between block-level siblings before assuming the math is wrong.
